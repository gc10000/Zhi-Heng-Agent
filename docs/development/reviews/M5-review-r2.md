## R2 · P1，未关闭：归档使已占用恢复无限递归

位置：[app/runs/repository.py](../../../app/runs/repository.py)第95—98行，`reconcile()`领取CAS失败后的自递归分支。

本轮已接受未归档路径的修复：已占用preparing窗口按旧冻结快照补齐claimed/用户消息，未占用路径保留支持版本门禁；`RunCommands.recover()`不再因`support_context_changed`跳过pending超时。首轮独立恢复反例通过，正式测试还覆盖实例重建、过期释放、领取前纠正、并发恢复和旧run不能释放新占用。

但新增`if latest.active_run_id == rid: return self.reconcile(...)`没有判断CAS失败是否来自`archived=True`。公开会话PATCH允许归档当前有占用的会话。此时`archived=False`领取条件永久不匹配，而自身占用指针仍相等，每次递归都读取同样的状态，再次失败。

独立反例通过实际领取函数，在占用CAS后、claimed写入前注入进程退出；用户纠正设备，再使用真实HTTP PATCH归档会话，返回200。新RunRepository/RunCommands将时钟推进一小时后恢复：先用最多4次重入的探针确认不前进，再用完全未包装的`reconcile()`直接执行，实际抛出`RecursionError`，留下`pending/preparing`和原占用。没有人工清除占用，也没有把探针防护触发冒充生产异常。恢复扫描异常会阻止本次扫描继续处理其后账本条目。

修复要求：领取失败后按实际拒绝原因有界退出；归档和其他无法恢复的会话应进入明确终态或可完成的清理路径，仅释放本run占用。不能无条件自递归或仅捕获`RecursionError`继续忽略。正式回归至少覆盖已占用preparing归档、已claimed/pending归档、重复/并发恢复、同账本另一会话仍能补偿，以及旧run不能清理新占用。保留本轮未归档恢复与领取前版本门禁。

## R3 · P2，未关闭：撤回设备后旧型号从会话历史重新进入正式计划

位置：[app/support/commands.py](../../../app/support/commands.py)第33—35行，`product_context()`；消费位置为[app/runs/query_runner.py](../../../app/runs/query_runner.py)第130—146行。

`clear_slots`写null/未确认/unknown、撤回来源/时间/操作者及历史的实现可接受。当前Vue已明确拦截直接清空，提示使用“设为未知”；独立实际Vue协议探针验证零请求提示及显式`clear_slots=['environment']`提交、字段清空、版本递增、无pageerror。旧run和确认草稿快照不变的正式回归也通过。因此首轮“静默保留字段”的直接症状已修复。

遗漏在正式消费者：设备被撤回后`product_context()`返回`None`，与“没有支持设备约束”混为一类。QueryRunner仅在返回值非None时覆盖旧选择和历史；结果仍让会话旧`product_ids`、助手快照或目录唯一型号重新确认刚撤回的设备。新增必需槽位测试只验证支持聚合的澄清提示，没有运行下一轮正式产品计划。

独立真实Mongo＋注入模型反例：先正常完成AX-24问答并确认支持设备，再`clear_slots=['device']`，当前支持槽位确为null且提示重新确认设备。随后不传任何`product_ids`、不在问题中提供型号，仅问“它的电源电压是多少”，正式`QueryRunner.execute()`却以`reason=confirmed_context`、`route=answer`、`slots.device=AX-24`完成回答；没有停在`awaiting_input`。注入模型只用于验证真实接线，不是付费供应商调用。

修复要求：设备撤回必须构成明确的未来主体边界，阻止旧会话选择、历史助手快照和目录唯一项自行恢复确认；没有本轮新显式型号或用户重新确认时应澄清。保留历史消息与旧run/确认记录快照，不靠删除历史解决。正式回归应跑到产品计划和实际问答入口，覆盖有旧会话选择、有旧助手确认、目录仅一个型号、无新product_ids，以及用户随后明确指定新型号仍正常工作。补充可选事实在真实历史中的撤回优先级检查，不能只将`_recent_messages`设为空就宣称所有未来上下文已验证。
