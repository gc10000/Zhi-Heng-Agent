## AF-R1-R／P2：列表制表符展开使合法跨行代码被改写

定位：`app/runs/answer_markdown.py:39–48`及54–55行。实际Markdown解析会在列表续行部分消费制表符缩进，并将剩余列展开为空格；新映射保留原文制表符，却用`text.find(content)`要求与已经展开的token行逐字一致。查找失败后跳过整个inline token的代码保护范围，最终把合法代码当正文过滤。

精确合成输入用Python字面量表示，`\n`与`\t`分别是换行和实际制表符：

```python
source = '- `first\n\t<ADDRESS> ![example](asset://other)`'
```

真实`MarkdownIt('default', {'html': False})`将其识别为列表中的单个`code_inline`；其inline内容为反引号、`first`、换行、两个空格及剩余代码。原文对应续行却以制表符开头，不能作为逐字子串匹配。当前`code_ranges(source)`为空。

结果：`<ADDRESS>`前新增反斜杠，图片语法示例被替换为“图片未在授权来源中登记”。反斜杠位于代码内，会作为可见代码字符保留；图片示例也已失去原文。这是代码内容损坏，不能因拒绝图片而视为正确。两类文字分别独立红测；整串及1／2／7字符的8条前后诊断均复现。修前被审实现（源码SHA与既有封存一致）在相同输入上保留原文；等效空格缩进及制表符紧跟列表标记的控制例通过。因此可定位为本次新映射回归，不是缺少PDF、模型输出差异或供应商分段造成。
