## 2. 必须处理的发现

### R1 · P1 · 同名独立章节仍可能跨章节合并（M0-06 重开）

位置：`app/import_process/agent/nodes/node_document_split.py:211`–`220`；关联标题切分/长块切分 `step_2_split_by_titles`、`_split_long_section`。

当前 `same_parent` 只比较 `parent_title` 文字。旧解析路径没有 `section_id`/`heading_path`，这些字段均缺失时，`same_boundary` 会把缺值当成相等。同文件两个独立“## 配置”章节经长块拆分后，会把第一章第 3 块与第二章第 1 块合并。

正常函数路径复现：

```python
content = (
    '## 配置\n' + ('A' * 65 + '。') * 3
    + '\n## 配置\n' + ('B' * 20 + '。') + ('B' * 80 + '。') * 3
)
sections, _, _ = step_2_split_by_titles(content, 'review-synthetic')
chunks = step_4_refine_chunks(sections, 100)
# 实测一个 chunk 同时包含 A 和 B，merged_parts == [3, 1]。
```

影响：A05 的“缺结构标识时保守不合并、独立章节不合并”验收尚未满足。标题重复的手册会混入另一个章节的内容。该漏洞是原合并设计的残余，并非声称 M0 新引入了所有跨章问题；本轮应完成已承诺的保守边界。

修复要求：在标题拆分时为每个实际章节实例生成本轮可靠身份，并在子块传播；或在缺少可靠身份时一律禁止跨输入章节合并。仅比较相同标题文字、文件名、相邻位置或 part 数值不足以证明同一章节。无需提前完成 M1 的持久知识注册系统。

验证要求：将上述完整 `step_2 → step_4` 路径加入正式红绿回归；覆盖同名不同章节、同源同章节合法子块合并、缺结构标识、表格、产品/来源、输入不变和大小边界。不能只测试手工传入不同 section_id 的理想输入。

### R2 · P2 · 图片验收可把错误图片或非图片响应判为通过

位置：`scripts/verification/resume_m0_live.py:130`–`138`、`scripts/verification/verify_m0_live.py:162`–`169`。

当前以 URL 包含隔离前缀、HTTP 200、响应非空作为图像成功条件，未验证预期拓扑对象身份、响应 hash、图像可解码及正文图与 final 图的关系。续验脚本还不检查 URL 的精确 origin/bucket/key；未知站点只要路径含相同前缀也可命中。

离线合成反例：给任意 URL `https://example.invalid/bucket/m0-test/review/wrong-image.jpg`，fake 响应为 `200` 和 HTML 非空正文，现有三个图片布尔条件全部为 True。此处只模拟现有检查表达式，**没有发出 HTTP 请求**。

修复要求：从已复制对象清单核对准确 origin、bucket、key 和 hash；由来源手册人工确认预期拓扑图，记录对应对象 hash/证据说明；回答内引用和 final 图片应包含/关联该预期图。下载验证 Content-Type、可解码图像及实际内容 hash，拒绝跳到未知 origin。非图片、其他同前缀图片或未知对象不得通过。允许 final 包含其他合法入选证据图，但预期拓扑图必须存在且匹配。

验证要求：纯离线覆盖错误图片、HTML 200、跨 origin、未知对象、正文/final 不一致及正确对象；Docker 恢复后再用同一检查验证真实图片。不能用一个“图片 URL 存在”的条件替代正确图文关联。

### R3 · P1 · 真实图片链路与默认冷启动仍缺验收证据

关联：M0-09、`records/M0-09.md`、`baseline-manifest.json`。

两题真实通过可保留；图片题已经失败，但当时未保存业务异常原因链。随后 Docker 故障只证明**阻断重试**，不能据此判定 Docker 就是原图片失败原因。两次原生模型加载异常后，仅预热路径通过，也不能证明默认冷启动已稳定。

验证要求：先恢复已有 Docker Linux 引擎并核对原容器健康；复用原隔离小样和会话，不重建集合或重复复制对象。只续验失败图片题，采集脱敏根因，必要时补正式回归与修复，再验证 R2 的正确图像身份、HTTP 与答案/终态/历史一致性。保留原已知题与追问的成功证据，但若修复影响它们的路径，则定向复验。

冷启动另起全新 Python/应用进程，以正常配置、不加验收脚本专有预热或线程覆盖，验证模型加载与一次真实查询成功，记录命令、退出码、设备、终态及保存次数。若确需初始化或并发策略调整，作为实际运行方案显式实现、解释并测试，不能只依赖测试脚本临时预热。无需重新全量解析或升级模型。

本项是代码与外部环境共同限制的验收缺口，当前保持未完成，不能用离线 fake 测试替代。宿主故障排查可以非破坏方式开展；重置 Docker/WSL、清卷或删除 socket 不在本次审查授权范围。
