## 已核实的工程缺口

- `review_feedback()`只在反馈文档里建立草稿。`bind_revision()`仅接受revision，`quality-proof`读取validated资料修订；两者不能充当regression复评接口。
- `Question`拒绝未知字段；不能随意向题目塞入feedback_id绕过schema。题目标注已有`independent_assistant_review/reviewed`身份和审阅文档、提交、内容指纹要求，合法独立助手可审标签；这不等同答案human双轮。
- `EvaluationCatalog`从受控路径读取JSONL、manifest与配置；HTTP只登记已配置版本。实验已有完整题集/配置指纹与同题集baseline约束，反馈来源目前未进入受支持的实验身份链。
- 运行账本和知识目标库必须明确区分。执行报告披露正式M2控制账本当前未核实，本轮也没有查询正式账本；不得把其他库空查询解释为历史记录不存在。

## 推荐接续设计，供执行端实施前具体化

范围属于跨模块的来源/版本接线。复用既有Question、来源跨度、manifest、catalog、ReviewService和Run恢复协议；新增最小不可变来源与复评证明链，不建立另一套评测器。

对比三种路线：只加feedback_id无法证明被审内容与实际执行范围；每条反馈都重建整套题集会给未变题目引入无必要的版本与校准工作。推荐**精确绑定已有冻结dev题，内容有变化时才派生新版本**。这是接续建议，尚未实现，不把设计文档当作执行能力。

1. **标注审核**：从真实已确认regression草稿构造完整候选Question及原件证据，保存不可变审核记录和内容指纹。区分草稿创建者、标签审阅者和human答案审阅者；助手可用合法独立身份完成标签核对，不能自签独立结论或代填human。
2. **冻结与来源绑定**：若已有dev题的完整内容/标签/证据和审核状态满足要求，明确绑定该题、dataset/manifest及题级SHA；若增加或修改题目/标签/证据，则另建父版本指纹可核验的新JSONL/manifest，旧文件不改。关联不只是题号，还要绑定feedback/draft审核版本、来源Run及结果指纹、精确资料修订与原件/证据、题目内容和审核记录。新增来源记录自身不可变且有hash，不回填旧实验。heldout不成为反馈回归目标，不自动迁移问题族。
3. **正式消费者**：通过受控catalog解析和登记，实际创建/运行实验时由服务端核验来源记录，并把绑定hash纳入请求、实验、题级检查点身份。控制库与Run/知识目标库分离也要验证；不能只在报告里追加source字段。不同来源/版本不能复用不相容请求或改绑旧检查点。
4. **regression复评证明**：独立接口从服务端取得已完成实验、当前result_attempt/题级结果及ReviewService门槛，证明覆盖被绑定回归题、范围/版本一致、顺序有效且来源未变化。时间先后不足以证明反馈关联；客户端分数/通过标志不能充当证明。候选仍须在同范围基线有效预校准后创建；题集真的变更时不得把旧r3/旧单题当成新版本基线。证明不能自动发布知识或宣告M6通过。
5. **幂等与恢复**：相同完整请求复用、异内容409、CAS/唯一约束、撤权拒绝、并发胜出和跨文件/数据库中断恢复。新文件先验证后登记，登记半途失败可用相同身份恢复；不删除历史、不改state/lease/slot。注册和证明分别执行，不让半完成登记被运行或被认可为已复评。
