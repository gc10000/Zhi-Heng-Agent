# Docker日志限额与D盘空间回收

日期：2026-10-31，Asia/Shanghai。用户明确授权先解决本机Docker占满D盘问题。本次是运维修复，不是M6质量复审；M6仍5/7、04保持验收、05／08未验收，M7未启动。另一执行端同时修改单题风险准入业务源码，其工作已独立提交为`1cceb9e`；本次保留且不混入运维提交。

## 根因与处理

实查Docker数据盘为`D:\Docker\DockerDesktopWSL\disk\docker_data.vhdx`。维护前D盘仅约1.42 GiB空闲，VHDX约163.99 GiB。Milvus容器标准输出日志为128727786682字节（约119.89 GiB），Mongo容器日志为1604145037字节（约1.49 GiB）；项目全部运行容器使用`json-file`但没有容量／文件数限制。Milvus业务数据卷约110 MiB，不能把巨型运行日志误认成知识切片体积。

`compose.yaml`新增共享日志配置，7服务统一`json-file`、`max-size=20m`、`max-file=3`，每服务约60 MB上限；包括当前不运行的两个worker。只修改日志配置，镜像和生效环境均与原容器核对一致；不拉镜像、不构建、不启动worker。

先确认实际控制库和目标库无正在运行的正式Run／实验，封存原容器／挂载、Milvus集合和关键条数、Mongo库名及Milvus／Mongo各10000行运行日志尾部。随后通过正常Compose容器重建应用轮转，复用原知识库命名卷，由Docker生命周期回收旧巨型运行日志。没有直接删除或截断Docker内部文件。旧标准输出日志未完整归档，仅保存尾部样本；这是用户授权回收的运行日志，不是已封存的M6原流／失败证据。

回收后Docker内部占用降至约36 GiB，但Windows仍未返还对应空间。第一次直接通过WSL执行TRIM遇到`Wsl/Service/0x8007274c`，失败保留；改用本机已有Alpine、无网络、无日志、一次性容器进入既有Docker挂载命名空间执行TRIM，回收约1.7 GiB可裁剪块，不接触业务文件。

普通Windows进程的只读虚拟磁盘API返回拒绝访问。经系统管理员确认启动限定单文件的隐藏维护助手；正常停止全部7个原运行容器和Docker Desktop，确认VHDX可独占打开后，只对上述已核实的Docker数据盘执行`compact vdisk`。无删除、格式化、迁移或VHDX替换。管理员助手、固定目标、started／result及DiskPart日志仅留本机新证据目录。

实际核验：

- 项目5个运行服务的`HostConfig.LogConfig`均为上述轮转选项；7服务展开配置亦一致。Milvus已实际产生当前日志、`.1`、`.2`三份，历史两份约20000000字节，证明发生了轮转，而不只是配置文本通过。所有容器目录采样合计约71 MiB，原超大日志已回收。
- 原8个卷挂载引用对应的卷均仍存在；全部业务命名卷沿用。Mongo镜像声明的旧空匿名`/data/configdb`卷仍存在未删除，新容器的同类空卷不是知识库数据卷；`/data/db`仍为原命名卷。
- 原897个Milvus集合清单完全一致，原4个非测试集合及本次筛选的关键M6集合条数与维护前一致。
- 维护前13469个Mongo库全部保留，无缺失；第二轮核验出现12个并行执行端新建的测试库，未假称全机没有并行活动。本次维护不创建测试库、不创建正式Run或质量记录。
- 336／597／1314三份已知历史保护清单逐文件hash匹配，组间重叠。未读取private-identity，未扫描或修改旧原始证据。
- Compose配置解析通过，命名卷映射、原镜像ID及有效环境一致，旧业务源码未纳入本次修改。

核验限制：库名／集合及关键条数相同不等于全库所有文档逐条内容hash证明；本次没有在共享现场做全库业务扫描。测试Mongo和Attu不属于项目Compose的日志治理范围，本次保留原容器和配置，其日志采样仅约15 MiB与数KiB；没有借维护扩大重建范围。
